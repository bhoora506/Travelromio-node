# N3-A Authentication Architecture

## 1. Authentication Mechanism
The chosen authentication mechanism is **Laravel Sanctum**. The Node.js application seamlessly verifies Sanctum-issued `PersonalAccessToken` values in exactly the same cryptographic manner as Laravel, without duplicating table structures or inventing new tokens.

## 2. Credential Source
The token is provided by the client via the `Authorization: Bearer <token>` HTTP header.

## 3. Credential Format
Tokens generated by Laravel Sanctum (and verified by Node) follow the plaintext format:
`{id}|{plainTextToken}`
(e.g., `1|abcd1234efgh5678...`)

## 4. Verification Process
Node.js verifies the token strictly as read-only via these exact steps:
1. Split the token by the `|` delimiter.
2. Lookup the database `personal_access_tokens` table for the primary key `id`.
3. If not found, abort (401).
4. If `expires_at` is present and past, abort (401).
5. Extract the plain text segment and compute its SHA-256 hash securely using `crypto.createHash('sha256')`.
6. Convert both the computed hash and the stored `token` hash from the database into Buffers.
7. Verify their lengths are identical.
8. Compare them securely via `crypto.timingSafeEqual` (constant-time check).
9. Ensure `tokenable_type` equals `App\Models\User`.
10. Abort (401) on any failure.

## 5. User Identity Mapping
After successful token verification, the corresponding user is fetched via the `tokenable_id` foreign key.
`personal_access_tokens.tokenable_id` -> `users.id`

## 6. req.user Contract
The middleware attaches a minimal, safe identity object to the request lifecycle (`req.user`).
Fields exposed:
- `id` (BigInt): The precision-safe BigInt primary key.
- `name` (String): User's full name.
- `email` (String): User's unique email.
*Safety Guarantee*: No password hashes, internal DB secrets, or raw bearer strings are attached.

## 7. Middleware Flow
Request -> `authenticate` middleware -> `authService.verifySanctumToken()` -> `req.user` -> Downstream routes.
Any failure yields a deterministic `401 Unauthorized` without exposing inner DB stack traces.

## 8. Authentication Errors
- **Exception Class**: `UnauthorizedError`
- **HTTP Status**: `401`
- **JSON Payload**: `{ "message": "Unauthenticated." }` (Precisely matching the expected Flutter client mapping).

## 9. HTTP Status Codes
- `401 Unauthorized`: Missing header, invalid scheme, malformed token, non-existent token, expired token, mismatched hash, deleted user.
- `500 Internal Server Error`: Only thrown if a network partition with MySQL occurs.

## 10. Security Decisions
- **No Token Modification**: To adhere strictly to N3-A read-only DB requirements, the Node implementation **does not update** the `last_used_at` timestamp.
- **Constant Time Hash Checks**: Uses Node's native `timingSafeEqual` to avoid timing side-channel attacks during hash validation.
- **Strict Buffer Checks**: Buffer length validation occurs before comparison to prevent buffer overflow/mismatch exceptions in Node's crypto library.

## 11. Token Lifecycle
Tokens are issued by Laravel upon login and stored in MySQL. They are revoked by Laravel upon logout. Node.js purely consumes (verifies) them statelessly.

## 12. Logout / Revocation Behavior
Node.js inherently supports Laravel's token revocation. If Laravel deletes a row in `personal_access_tokens` (via `/api/logout`), the Node.js middleware instantly returns 401 for that token.

## 13. Laravel Compatibility
100% Behavioral Compatibility.

## 14. Flutter Compatibility
100% Behavioral Compatibility (Flutter's `UnauthorizedException` handler relies on HTTP 401).

## 15. Database Dependencies
- Table: `personal_access_tokens`
- Table: `users`
(All operations performed as `SELECT` read-only).

## 16. Intentional Node Improvements
- **Read-Only Verification**: The `last_used_at` timestamp is intentionally left untouched during token verification to strictly respect the constraint of read-only access for this backend node layer during migration. (If required for auditing later, a transaction could be added).

## 17. Known Limitations
- Modifying `last_used_at` timestamp is skipped to respect DB integrity limits.

## 18. Test Strategy
An isolated test harness (`scripts/test-auth.js`) injects mock dependencies to test 14 complex permutations of string splitting, hashing, length checks, expiration limits, and identity resolution without polluting the real database.

## 19. Exact Verification Commands
```bash
npm run test:auth
```
